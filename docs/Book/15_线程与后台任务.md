# 第 15 章：线程与后台任务——让窗口始终能够响应

[上一章：样式资源与界面设计](14_样式资源与界面设计.md) · [阅读地图](00_阅读地图与学习方法.md) · [下一章：外部进程与实时日志](16_外部进程与实时日志.md)

本章目标：解释窗口卡顿的原因，写出有进度、能取消、失败可见、关闭安全的后台任务。先理解前面的信号、事件循环和对象生命周期，再阅读本章。

## 1. 为什么按钮点下去以后窗口变白了

设想按钮的槽函数里需要处理一万个文件。Python 从第一行执行到最后一行，在槽函数返回以前，GUI 主线程一直忙着处理文件，没有机会处理窗口重绘、鼠标点击和关闭事件。操作系统发现窗口迟迟不响应，就可能显示“未响应”。

这和 MFC 的窗口消息循环被长时间处理占住很相似。`app.exec()` 驱动的事件循环需要不断取出并处理事件。**事件循环正在运行，不代表它永远有空处理下一个事件。**

下面的代码就会阻塞界面，即使只暂停三秒：

```python
def on_clicked(self):
    import time
    time.sleep(3)  # 当前槽在主线程执行，主线程同时睡了三秒
```

把循环搬进 `QTimer.singleShot(0, ...)` 也不会自动变成后台任务。定时器到时，槽仍在所属线程执行。只有把工作切成很短的小块，每次处理一点并及时返回，定时器方案才有意义。

## 2. 线程解决什么问题

进程是正在运行的程序；线程是进程内部的一条执行路线。GUI 主线程负责窗口，工作线程负责耗时处理，它们通过信号交换结果。

三个必须记牢的边界：

1. `QWidget` 及其子类只能在 GUI 主线程中创建和操作。后台线程不能直接调用 `label.setText()`。
2. 把对象放进线程，不代表调用它的普通 Python 方法就会自动切换线程。`worker.run()` 是直接调用，发生在调用者当前线程。
3. 线程可以改善响应性，但在常见启用 GIL 的 CPython 中，多个线程不能让纯 Python 的 CPU 密集循环按核心数成倍提速。重计算考虑进程；I/O、会释放 GIL 的库调用和保持 GUI 响应仍是线程的常见用途。

新手容易把 `QThread` 对象理解为“工作代码必须写在里面的容器”。更准确的理解是：`QThread` 管理一条线程，`Worker(QObject)` 承担具体工作。`QThread` 对象本身通常创建并留在主线程；`worker.moveToThread(thread)` 改变 worker 的线程归属。

## 4. 按数据流拆解代码

`Worker` 声明四个信号：`progress(int)` 传递进度；`result(str)` 传递完成或取消说明；`failed(str)` 传递异常详情；`finished()` 表示“这次执行已经结束”。`finished` 的意义包含成功、失败和取消，所以放在 `finally` 中发出。

窗口启动时保存 `self._thread` 和 `self._worker`。这样既保持 Python 引用，也能记录“当前已有任务”。开始按钮禁用只是界面表现，`if self._thread is not None` 才是第二道状态检查，避免以后通过快捷键或其他入口重复启动。

关键连接如下：

```python
worker.moveToThread(thread)
thread.started.connect(worker.run)
worker.progress.connect(self.progress.setValue)
worker.finished.connect(thread.quit)
worker.finished.connect(worker.deleteLater)
thread.finished.connect(self.thread_finished)
thread.finished.connect(thread.deleteLater)
thread.start()
```

启动后，`run` 在 worker 所在线程执行。进度信号跨线程到 GUI 对象，其槽在主线程处理。工作结束后，请求线程事件循环退出，并安排删除 worker。线程真正结束后，窗口才恢复按钮、清空引用，最后安排删除线程对象。

`deleteLater()` 表示按 Qt 的生命周期规则安排删除，不是立刻执行 Python 的 `del`。跨线程对象需要在合适的线程中清理，不能凭感觉在任意地方直接销毁。

## 5. 取消不是强行打断任意一行

窗口调用 `thread.requestInterruption()`，只是设置取消请求。worker 在每轮循环里检查：

```python
if QThread.currentThread().isInterruptionRequested():
    self.result.emit("任务已经取消")
    return
```

这叫协作取消：工作者在安全位置主动退出。因此取消的响应速度取决于检查间隔，以及一次工作步骤最长会阻塞多久。实际网络、串口或文件库调用必须设置合理超时，否则取消标记也救不了永远不返回的调用。

为什么不写一个 `worker.cancel` 槽，再发信号给它？因为本例的 `run()` 是持续执行的长槽；它占用工作线程时，该线程不能同时处理队列中的取消槽。取消信号可能要等工作做完才轮到执行。`requestInterruption()` 是适合这个模式的线程安全请求，不需要 worker 的事件循环先处理取消槽。

也不要依赖 `thread.quit()` 来中断长循环。它请求结束事件循环，不会把正在执行的函数从中间切断。更不要用 `QThread.terminate()` 常规取消；任意时刻强杀线程可能留下未释放的锁、损坏的状态或半写入的数据。

## 6. 运行中关闭窗口为什么需要两步

如果窗口销毁时工作线程仍在运行，可能出现 `QThread: Destroyed while thread is still running`，甚至进程异常退出。

示例的 `closeEvent` 先标记 `_closing`、请求取消并 `event.ignore()`，让窗口暂时保留。GUI 继续处理事件，因此能够收到 `thread.finished`。结束槽再通过 `QTimer.singleShot(0, self.close)` 发起真正的关闭。

不要在主线程的关闭事件里无限期 `thread.wait()`。它会让窗口再次卡住；某些清理过程需要主线程处理信号时，还可能形成互相等待。异步等待线程结束的设计更符合桌面程序的工作方式。

## 7. 常用 API 小表

| API | 输入 | 返回值与作用 |
| --- | --- | --- |
| `QThread(parent)` | 可选父对象 | 创建线程管理对象，尚未运行 |
| `moveToThread(thread)` | 目标 `QThread` | 改变无父对象的 worker 的线程归属；不同 Qt 版本返回类型有差异，不依赖返回值写业务逻辑 |
| `start()` | 通常不传参数 | 请求启动线程，立即返回，结果由信号观察 |
| `requestInterruption()` | 无 | 请求协作取消，不等待任务结束 |
| `isInterruptionRequested()` | 无 | 返回 `bool`，供 worker 检查 |
| `quit()` | 无 | 请求线程事件循环退出，不中断长函数 |
| `isRunning()` | 无 | 返回线程当前是否运行的 `bool` |
| `deleteLater()` | 无 | 安排对象延迟销毁，不返回业务结果 |

`QThreadPool` 和 `QRunnable` 适合许多独立短任务；先把本章的生命周期弄明白，再考虑线程池，避免同时学习两套管理方法。

## 8. 常见错误与练习

后台修改控件、给准备迁移的 worker 设置 GUI 父对象、仅禁用按钮却不保存任务状态、只在成功路径发 `finished`、退出时直接丢掉线程引用，都是典型问题。排查时先回答三个问题：这段代码在哪条线程执行？谁持有对象？失败路径是否也能结束？

练习：

1. 把任务改成分批检查 100 个虚拟文件名，进度信号带上当前文件名。
2. 增加“已耗时”显示；计时用 GUI 中的 `QTimer`，不要在 worker 里修改标签。
3. 连续测试“开始—取消—再开始”十次，确认不会出现两个任务同时运行。
4. 将一步耗时临时改为两秒，解释取消为什么变慢，然后把一步拆成小步骤。
5. 画出开始、运行、取消中、结束、关闭之间的状态转换。
