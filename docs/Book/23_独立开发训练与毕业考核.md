会跟着示例运行，与能够独立完成需求，中间还有一段距离。这一章的训练故意不给完整实现。你可以查官方文档、看报错、复习概念，但先不要打开第 22 章对应功能的代码。

## 23.1 从需求到代码，需要先写的五样东西

以“配置文件管理器”为例，先写清楚：谁用它、输入和输出是什么、什么时候写入文件、出错后保留什么、怎样证明完成。然后准备五份小材料，每份几行即可：

1. **用户流程**：打开文件 → 展示表单 → 修改 → 校验 → 保存 → 显示结果。
2. **控件树**：主窗口、中央区域、表单、按钮区、状态栏分别包含什么。
3. **数据结构**：字段名、类型、默认值、限制，哪些是运行状态，哪些要保存。
4. **状态转换**：未打开、已打开、已修改、保存中、保存失败如何切换。
5. **验收清单**：正常输入、空值、坏文件、取消、重复点击、运行中关闭。

这一步可以省下大量“写到一半才发现不知道应该怎样”的时间。它不是为了把简单需求写成厚文档，而是把真正会影响结果的决定提前说清楚。

## 23.2 三种不同的练习方式

**复写**用于巩固。看过例子后关掉它，用自己的变量名重新完成。目标不是字面一致，而是行为一致并能解释。

**迁移**用于证明理解。学了任务管理器，就做书籍清单或服务器配置管理器。数据字段不同后，你必须重新判断验证、保存和显示逻辑，照抄的局限就会暴露。

**排错**用于工程能力。故意把 `connect(handler)` 写成 `connect(handler())`，把保存路径改为不存在的目录，把模型行号和代理行号混淆。每次先记录现象、猜测和验证，再修正。不要在已有重要数据上做破坏性实验；使用自己的临时练习目录。

## 23.3 四个递进任务

| 任务 | 需求 | 通过标准 |
|---|---|---|
| A：端口表单 | 输入主机名与端口，端口限 1～65535；点击提交显示规范化结果 | 空主机拒绝，端口无法越界，键盘能完成提交 |
| B：文本便签 | 新建、打开、保存、另存为，支持中文和未保存退出确认 | 文件选择取消无副作用，写入失败不清除修改标记 |
| C：批量演示任务 | 处理 100 个模拟条目，显示进度，可取消 | 界面可拖动，不能重复启动，结束前关闭会安全收尾 |
| D：日志启动器 | 启动本机一个固定演示程序，显示输出和退出码 | 启动失败、正常退出、主动停止均有明确状态 |

每完成一个任务，请把实现限制写在说明中。例如批量演示只模拟等待，没有真正处理图片；知道边界并准确表述，也是独立开发的一部分。

## 23.4 毕业项目：本地连接配置管理器

请独立完成一个管理连接资料的桌面工具。它不需要真的连接远程机器，所以不涉及服务器、账号或网络环境；重点放在信息管理与状态正确。

每条配置包含稳定编号、名称、主机、端口、协议（TCP/UDP）、备注、是否启用。允许添加、编辑、删除、按名称或主机搜索、按端口排序。名称与主机去首尾空白后不能为空；端口为 1～65535 的整数；协议必须来自固定选项。名称是否允许重复由你明确决定并在说明中保持一致。

用 JSON 保存，包含格式版本。程序应能新建、打开、保存、另存为；打开失败保留当前内容；写入失败保留未保存标记；关闭时支持保存、放弃、取消。导出后重新导入应保留全部业务字段。界面应支持缩放与键盘操作，选中状态与按钮可用性一致。

至少包含一个纯 Python 数据模块、一个文件仓库、一个界面模块和入口。数据层不应导入 `QWidget` 或弹 `QMessageBox`。界面使用 `QTableView` 加数据模型，并说明排序代理的索引如何转换。本轮考核统一使用 JSON 仓库，与下面的坏 JSON、格式版本和文件保存验收保持一致。通过后可以把 SQLite 作为单独的扩展练习，再为数据库设计相应的迁移与备份规则。

需要交付源文件、依赖清单、运行说明、测试、打包结果及验收记录。打包结果至少在一个不依赖你开发目录的环境中运行；无法获得干净机器时，准确写明尚未完成该项。

## 23.5 先验收行为，再评价代码

| 场景 | 应有结果 |
|---|---|
| 创建两个相同端口、不同编号的记录 | 仍能独立编辑和删除，身份不靠端口值 |
| 搜索后再排序，再删除一行 | 删除对应源记录，其他记录不变 |
| 打开损坏 JSON 或未知版本 | 明确提示，原文档不被清空 |
| 修改后关闭，点保存，再取消路径 | 窗口和未保存数据保留 |
| 导入 `"port": "abc"` 或 `"enabled": "false"` | 按规则拒绝，不能靠真假值隐式糊弄过去 |
| 多次打开、关闭编辑对话框 | 没有失效引用、重复连接、重复保存 |
| 保存到无权限或不存在的目录 | 错误被展示，界面仍可继续使用 |
| 移动安装目录或换工作目录启动 | 能找到资源，用户数据路径有明确约定 |

开发时不必等全部完成再做验收。每增加一个功能就跑相关场景，错误会更容易定位。

## 23.6 给自己评分，但不要用总分掩盖严重问题

功能与数据正确 40 分，错误与取消分支 20 分，结构可维护 15 分，测试与调试证据 15 分，运行和交付说明 10 分。80 分可视为完成基础训练。

无论总分多少，如果出现“排序后删除错记录”“保存失败还关闭并丢数据”“线程仍运行就销毁”“只有自己 IDE 能启动且原因不明”，应先修复再毕业。这些问题会直接影响程序是否可靠。

代码评价不要看目录数量、类数量或注释数量。看一个需求变更需要改几处、规则是否重复、函数是否能解释、错误是否能定位，以及测试能不能发现真实失误。

## 23.7 卡住时的自助流程

```text
能稳定复现吗？
  不能 → 缩小输入、记录步骤和环境
  能 → 是导入/启动、显示、交互、数据还是退出问题？
        → 缩成最少控件/最少数据
        → 断点或日志观察实际状态
        → 查对应类的文档和版本
        → 一次验证一个猜测
        → 修复后重跑原场景与相邻边界
```

例如“按钮没反应”，先在槽函数入口放断点。断点未命中就查连接、按钮是否禁用、是否被别的控件遮挡；断点命中就查输入、提前返回和后续错误。不要同时修改布局、连接和业务代码，否则即使好了，也不知道原因。

如果需要向社区提问，给出环境版本、最小代码、预期结果、实际结果、完整错误末尾以及已尝试的验证。避免只说“PyQt 不工作”。能把问题表述清楚，通常已经完成了一半定位。

## 23.8 从小项目继续成长

下一阶段按实际需求选择：数据多就深入模型视图和 SQL；处理文件多就学任务队列和取消；对接工具多就学进程协议与日志；界面交互复杂就学命令模式、撤销和状态机；要维护多年就加强依赖管理、兼容迁移、自动测试与发布流程。

大型项目经验来自持续处理变化。可以每周给毕业项目加一个有明确验收条件的需求，记录设计取舍，而不是反复从头抄新的完整项目。

本章自检：你能否在没有参考实现时，画出数据流、查到合适 API、写出第一条测试，并解释最可能失败的两个分支？如果可以，你已经具备继续独立成长的基础。
