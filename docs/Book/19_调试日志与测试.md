# 第 19 章：调试、日志与测试——从“能运行”走向“知道为什么正确”

[上一章：项目结构与分层设计](18_项目结构与分层设计.md) · [阅读地图](00_阅读地图与学习方法.md) · [下一章：打包发布与维护](20_打包发布与维护.md)

本章目标：建立一套能独立定位问题的方法，并知道哪些功能适合自动测试。所谓独立开发，并不是永远不出错，而是遇到错误时能收集证据、缩小范围、修复后验证。

## 1. 先分清是哪种问题

| 现象 | 首先检查什么 |
| --- | --- |
| 启动立即退出 | 从终端运行，查看 traceback 和 Qt 启动错误 |
| 按钮没反应 | 信号是否连接、槽是否进入、控件是否被禁用 |
| 窗口卡顿 | 主线程是否有长循环、同步 I/O 或阻塞等待 |
| 数据保存错误 | 输入、业务对象、序列化结果、实际文件路径 |
| 退出崩溃 | 线程、进程、定时器、跨窗口引用的生命周期 |
| 只在打包后失败 | 缺失资源、插件、路径假设和用户目录权限 |

不要一看到卡顿就增加线程，也不要一看到异常就加 `try/except` 包住全部代码。先确认问题属于哪一类，再选择工具。

## 2. 学会阅读 traceback

从终端启动程序，保留完整错误输出。traceback 最后一行告诉你异常类型和说明，例如 `AttributeError` 或 `FileNotFoundError`；往上找最后一个属于自己项目的文件和行号，再沿调用过程理解原因。

假设错误说 `NoneType` 没有某个属性，不要只在出错行前加 `if x is not None`。先追问为什么这里拿到了 `None`：没有选中列表项？窗口已经关闭？查询没有结果？不同原因需要不同产品行为。

记录复现步骤也要具体：“启动后新增两个任务，选中第二个，删除，再点击完成”比“偶尔报错”有用得多。最好同时记录 Python、PyQt、Qt 和操作系统版本。

## 3. 断点比猜测更快

在编辑器里给按钮槽第一行设置断点，点击按钮后观察：程序是否停在这里？参数值是什么？实例成员是否符合预期？

常用调试动作可以这样理解：单步越过执行当前这一行；单步进入查看被调用函数；继续运行直到下一个断点；调用栈显示“我怎样来到这里”。先掌握这四项已经足够解决很多问题。

调试器暂停主线程时，窗口暂时不响应是正常现象，不要把断点造成的暂停误认为程序自身卡死。线程问题还要看暂停的是哪个线程。需要观察正常时序时，结构化日志往往比反复断点更合适。

## 4. 把 print 逐渐升级为日志

`print` 很适合临时观察。应用需要长期维护时，`logging` 可以记录时间、级别、模块名和异常堆栈，并把输出写进文件。

下面是入口处可用的配置片段，`log_path` 应是用户可写目录中的路径：

```python
import logging
from logging.handlers import RotatingFileHandler

handler = RotatingFileHandler(
    log_path, maxBytes=1_000_000, backupCount=3, encoding="utf-8"
)
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
    handlers=[handler],
)
logger = logging.getLogger(__name__)
```

在各业务模块里用 `logging.getLogger(__name__)` 获取自己的 logger，不必每个模块都重新配置 handler。文件轮转限制日志大小，避免长期运行撑满磁盘。

选择级别时：`DEBUG` 记录排查细节；`INFO` 记录启动、保存成功等正常事件；`WARNING` 记录可恢复但值得关注的情况；`ERROR` 记录某次操作失败。捕获异常时用 `logger.exception("保存任务失败")`，它会附上当前异常堆栈。

错误消息可以同时有两个读者：给用户的“无法保存，请检查目录是否可写”，给开发者的实际路径、异常类型和堆栈。不要把访问令牌、密码或整份敏感内容直接记入日志。

## 5. 最小复现是独立解决问题的关键能力

如果一个 2000 行程序中的表格排序有问题，先做一个只含窗口、表格和三行固定数据的小程序。逐步移除无关内容，每删一部分都检查问题还在不在。

问题还在，说明剩余代码足以解释问题；问题消失，说明刚移除的部分或它的交互值得检查。这个过程常常在你准备求助以前就帮助你找到原因。

最小复现要保留必要条件，例如线程归属、对象是否有父对象、信号连接顺序。只截取报错的那一行通常不是复现。前面各章的独立示例就是很好的实验底板：一次改变一个因素，观察结果。

## 6. 先测试不需要窗口的规则

上一章把业务从界面提取出来，就是为了让许多测试不必启动 Qt。纯函数最容易开始：

```python
import unittest

def normalize_title(text):
    result = text.strip()
    if not result:
        raise ValueError("标题不能为空")
    return result

class TitleTests(unittest.TestCase):
    def test_removes_surrounding_spaces(self):
        self.assertEqual(normalize_title("  学习布局  "), "学习布局")

    def test_rejects_blank_title(self):
        with self.assertRaises(ValueError):
            normalize_title("   ")

if __name__ == "__main__":
    unittest.main()
```

这是可单独保存运行的教学片段。正式项目应让测试导入生产代码中的函数，而不是把实现复制进测试文件。测试的目的在于验证规则及边界，不是逐行模仿实现。

保存测试优先使用临时目录，验证保存后重新读取的结果。失败测试应模拟目录不可写、损坏 JSON 或缺少字段，避免误操作用户真实文件。

## 7. QtTest 与 QSignalSpy

`PyQt6.QtTest` 提供 `QTest` 模拟键盘鼠标操作，`QSignalSpy` 记录信号发射及参数。它们属于 Qt 的测试工具，并不是必须先安装 pytest 才能使用。

下面是最小的控件与异步信号测试：

```python
from PyQt6.QtCore import QTimer, Qt
from PyQt6.QtTest import QSignalSpy, QTest
from PyQt6.QtWidgets import QApplication, QPushButton

app = QApplication.instance() or QApplication([])
button = QPushButton("点击")
button.show()
click_spy = QSignalSpy(button.clicked)
QTest.mouseClick(button, Qt.MouseButton.LeftButton)
assert len(click_spy) == 1

timer = QTimer()
timer.setSingleShot(True)
timeout_spy = QSignalSpy(timer.timeout)
timer.start(20)
assert timeout_spy.wait(1000), "一秒内没有收到 timeout"
assert len(timeout_spy) == 1
button.close()
```

这里先创建 spy，再触发动作，否则可能错过信号。`wait(milliseconds)` 返回是否在等待期间收到信号，并让 Qt 有机会处理事件。它用于测试，不是应用业务中等待网络或线程的推荐写法。

不要用 `time.sleep(1)` 猜测异步任务已经完成。它可能阻塞需要发送信号的主线程，也会让测试在慢机器上偶发失败。等待明确的状态或信号，并设置上限，失败时才能及时报告。

## 8. pytest-qt 是另一层便利工具

`pytest` 是 Python 测试框架，`pytest-qt` 是第三方插件。插件提供 `qtbot` 管理控件、发送事件、等待信号，并处理常见 Qt 测试生命周期问题。

如果采用它，在学习虚拟环境中安装 `pytest pytest-qt`，并让测试配置使用 PyQt6。常见写法是 `with qtbot.waitSignal(worker.finished, timeout=2000): ...`；把触发任务的代码放在上下文内部，使监听先于动作建立。

先学 `unittest` 或 pytest 中的一套即可，再按需要引入插件。不要因为测试工具变多而推迟对输入校验、存储往返和线程关闭这些重要行为的验证。

## 9. 测试应该覆盖什么

优先覆盖可能损坏数据、难以手动重复、曾经出错的行为：空输入、重复操作、保存失败、损坏数据、取消、运行中关闭。布局外观、文字截断、高 DPI 和多屏行为还需要实际视觉验收；自动点击通过并不代表界面好用。

网络测试使用本地服务器或替身控制成功、错误和延迟。线程测试不要只测成功，要检查取消和失败后是否真的结束、是否可以再次启动。修复 bug 时补一个能复现原问题的测试，价值往往高于追求一个漂亮的覆盖率数字。

## 10. 练习与自检

1. 故意让一个槽访问不存在的属性，从 traceback 找到文件、行号和调用入口。
2. 为第七课添加日志，记录开始、取消请求、worker 结束和线程结束。
3. 给标题规则补上中文、换行、超长字符串三个测试，并明确预期行为。
4. 把某个 GUI 问题压缩成不超过 60 行的最小复现。
5. 写一张退出验收表，包含空闲关闭、运行关闭、失败后关闭和连续关闭请求。

自检：你是在验证行为还是实现细节？能否可靠复现失败？错误信息是否足够定位？测试是否会依赖互联网或真实用户文件？能回答这些，测试才真正支持开发。
