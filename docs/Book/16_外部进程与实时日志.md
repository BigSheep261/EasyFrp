# 第 16 章：外部进程与实时日志——让界面管理另一个程序

[上一章：线程与后台任务](15_线程与后台任务.md) · [阅读地图](00_阅读地图与学习方法.md) · [下一章：网络请求与异步思维](17_网络请求与异步思维.md)

本章目标：启动一个命令行程序，把它的输出实时显示在窗口里，并处理启动失败、停止、退出码和窗口关闭。这是开发编译工具、下载器、服务管理器、命令行工具图形前端时的基础。

## 1. 线程与进程怎么选

如果要运行当前 Python 程序里的一段函数，可以考虑线程。如果要运行一个已经存在的可执行文件，如 `git`、转换工具或自己的服务端程序，就需要管理外部进程。

进程拥有相对独立的内存空间。子进程里定义的 Python 变量不会自动出现在 GUI 程序里。二者通过标准输入、标准输出、标准错误、文件、套接字等明确通道通信。

`QProcess` 把外部进程的生命周期接入 Qt 事件循环。调用 `start()` 后马上返回；启动成功发 `started`，有数据发 `readyReadStandardOutput`，结束发 `finished`。因此它通常可以直接放在 GUI 主线程中使用，不需要为了读取日志再套一个线程。

这里的“异步”表示启动调用不等整项工作完成。程序之后通过信号告诉你发生了什么；它和“必须使用 Python `async def`”不是同一个概念。

## 2. 完整示例

代码：[第八课_进程日志.py](示例代码/第八课_进程日志.py)。在项目根目录运行：

```powershell
.\docs\Book\.venv\Scripts\python.exe .\docs\Book\示例代码\第八课_进程日志.py
```

示例使用当前 Python 解释器启动一个只打印中文日志的本地子进程：

```python
self.process.start(sys.executable, ["-u", "-c", CHILD_CODE])
```

`sys.executable` 是当前解释器的路径；`-u` 关闭 Python 标准流缓冲；`-c` 表示执行后面的字符串。这里的字符串固定写在教材中，不接收用户输入。教学用子进程会间隔输出 30 条日志，便于观察实时效果。

注意：这个例子按 Python 源码方式运行。通过 PyInstaller 冻结后，`sys.executable` 通常指向打包后的应用，不再是可用来执行 `-c` 的 Python 解释器。不要直接把本例冻结成程序后期待同样的子进程行为；发布真实工具时应明确被管理的可执行文件路径。

## 3. 程序路径与参数必须分开

`QProcess.start(program, arguments)` 接受程序路径和字符串参数列表。参数中的空格属于该参数的内容，Qt 会按平台规则传递。

```python
program = r"C:\Program Files\SomeTool\tool.exe"
arguments = ["--input", r"C:\My Files\任务.json"]
process.start(program, arguments)
```

上面展示调用形状，路径需要换成真实文件。不要把所有内容拼成一长串，也不要为了“方便”一律交给 `cmd /c`。shell 会额外解释重定向、管道、变量和特殊字符；把用户文本拼进 shell 命令可能产生意外执行。

程序依赖相对路径时，使用 `setWorkingDirectory(path)` 明确工作目录。它和“可执行文件在哪”是两件事。排查启动问题时记录程序路径、工作目录和参数，但避免把密码或令牌写进日志。

## 4. 一次收到的数据不一定是一行

`readyReadStandardOutput` 的意思是“现在有一些字节可读”，不是“现在有完整一行”。一次可能来半行，也可能来十行。中文 UTF-8 字符由多个字节组成；两次读取之间甚至可能把一个字拆开。

因此下面的做法不可靠：每次拿到一块字节就独立 `decode("utf-8")`，再用 `appendPlainText()` 加到界面。它可能报解码错误，也可能给原本一行插入多余换行。

示例使用增量解码器：

```python
decoder = codecs.getincrementaldecoder("utf-8")(errors="replace")
text = decoder.decode(chunk, final=False)
```

解码器保留块末尾不完整的字符，等下一块补齐后再输出。进程结束时调用 `decoder.decode(b"", final=True)`，把剩余状态处理完。`errors="replace"` 让损坏的字节显示替代字符；如果你需要严格校验协议，应改为报告解码错误。

示例用 `insertText` 插入实际文本，保留原有换行；并限制日志控件最多保留 2000 个文本块，避免长时间运行无限占用内存。真实高频日志还可以先放缓冲区，每 50 至 100 毫秒批量刷新，减少 GUI 更新次数。

## 5. 标准输出与标准错误

标准输出通常放正常结果，标准错误通常放诊断信息，但最终约定由被启动的程序决定。工具把进度写到标准错误并不一定表示失败，失败也不一定有可读文字。

本例使用 `MergedChannels` 合并两种流，方便展示一个日志窗口。这样会失去来源区分。若需要不同颜色显示，应保持分离，分别连接两个读取信号，并为每条流各保存一个增量解码器。

外部程序也必须及时刷新输出。即使 GUI 读取代码完全正确，子进程把日志留在自己的缓冲区里，界面仍收不到。示例同时使用 `-u` 和 `flush=True`；其他工具要查其文档中的无缓冲或进度输出选项。

## 6. 生命周期不能只处理正常完成

示例保存一个长期存在的 `self.process = QProcess(self)`，窗口作为父对象负责其 Qt 所有权，但**有父对象不代表运行中的子进程可以随意丢弃**。

开始时禁用开始按钮并设 `_busy`。启动成功收到 `started`；找不到程序、权限不足等情况触发 `errorOccurred`。其中 `FailedToStart` 需要单独恢复状态，因为启动失败时不能指望一定再收到 `finished`。

正常结束时，`finished(exit_code, exit_status)` 同时提供两个信息：退出码是外部程序约定的整数，通常 0 表示成功；退出状态区分正常退出和崩溃。某程序“正常退出但返回 1”仍可能表示业务失败；不要只判断它有没有崩溃。

结束前还要最后读取一次输出并结束解码器，否则最后几条日志可能丢失。正常完成、启动失败、用户停止都应最终恢复同一组按钮状态。

## 7. 停止和关闭

示例先调用 `process.terminate()` 请求结束，同时启动两秒单次计时器。如果子进程仍未停止，计时器调用 `kill()`，然后继续通过 `finished` 观察实际退出。

不同操作系统上的 terminate 行为有差异。Windows 中它常通过窗口关闭消息尝试终止；没有消息循环的控制台程序可能不响应，所以超时后的 kill 是必要的退路。真实工具若提供退出命令、标准输入协议或控制接口，应优先采用工具自己的正常关闭方法。

运行中关闭窗口时，示例忽略第一次关闭事件、发出停止请求，等子进程结束后再关闭窗口。整个过程不调用 `waitForFinished()`，GUI 主线程仍可处理日志和退出信号。

`kill()` 也不代表整棵进程树都受管理。如果工具还启动孙进程，是否会连带退出需要额外的操作系统级进程管理设计。本章例子只创建一个不再派生进程的子进程。

## 8. 常用 API

| API | 输入 | 返回值或通知 |
| --- | --- | --- |
| `start(program, arguments)` | 路径、字符串列表 | 不返回执行结果；之后观察启动或错误信号 |
| `state()` | 无 | `NotRunning`、`Starting` 或 `Running` |
| `readAllStandardOutput()` | 无 | `QByteArray`，用 `bytes(...)` 转 Python 字节串 |
| `errorString()` | 无 | 可读的错误说明字符串 |
| `terminate()` / `kill()` | 无 | 请求停止；完成仍由信号确认 |
| `setWorkingDirectory(path)` | 目录字符串 | 设置子进程工作目录 |
| `write(data)` | 字节数据 | 返回接受写入缓冲区的字节数或错误值；不代表对方已处理 |

## 9. 练习与验收

1. 故意把程序路径改成不存在的路径，确认启动失败后按钮能恢复。
2. 将子进程最后一条输出设为没有换行的文本，确认退出后仍能看见它。
3. 给 stdout 和 stderr 各建一个控件；每条流使用独立解码器。
4. 给界面增加运行时长和进程状态，不使用阻塞等待。
5. 连续执行启动、停止和运行中关闭，观察是否遗留子进程。

自检：为什么读取回调不代表收到完整一行？为什么退出码和退出状态都要看？为什么不需要另开线程读取这个示例的日志？能回答这些，你就掌握了管理外部工具最重要的边界。
