# 第 25 章　练习提示与参考思路

请先独立完成正文练习，再打开这一章。这里给出各阶段代表性问题的推理路线和判断标准，不是逐道练习的唯一答案。相同需求可能有多种合理实现；关键是行为正确、边界清楚、能解释原因。

## 25.1 基础阶段：为什么窗口程序不像顺序脚本

问题：把 `print("之后")` 写在 `app.exec()` 后，为什么显示窗口时没有立刻打印？

提示一：先想 `exec()` 是否已经返回。提示二：窗口出现后，程序仍在事件循环中处理输入和绘制。参考结论：关闭最后一个窗口通常会让默认配置的应用退出事件循环，随后才执行后面的语句。显式退出、是否在最后窗口关闭时退出等设置会改变条件，所以不能把它描述为永远不会返回的死循环。

问题：`button.clicked.connect(save())` 为什么不对？

先按普通 Python 求值顺序解释：Python 先调用 `save()`，再把返回值传给 `connect()`。通常返回值是 `None`，并不是一个可调用的接收者。正确思路是把函数对象交给连接，等点击时再调用。若需要附带自己的参数，可以定义一个适配函数或 lambda，同时处理信号可能带来的参数。

问题：修改窗口中已有标签，应该重新创建标签吗？

参考思路：先找到原标签对象的引用，再调用 `setText()`。新建另一个同名局部变量不会自动替换布局里的旧控件。分清变量、对象和父子树，比记住某个具体修复更重要。

## 25.2 布局与表单：不要先算像素

任务：实现“左边名称和端口，右边连接状态，底部按钮”。

先用纸画三个区域，再决定外层纵向、上层横向、表单使用 `QFormLayout`。窗口伸展时让内容区获得空间，按钮保持合适尺寸。`stretch` 决定额外空间如何分配，但还受控件最小尺寸和 `QSizePolicy` 约束。

验证顺序是：窗口变窄、变高、系统文字放大、输入很长、Tab 切换焦点。只有默认尺寸截图好看不够。不要用 `setFixedSize()` 掩盖布局问题。

表单提交参考步骤：读取 → 去首尾空白 → 类型/范围/业务规则验证 → 成功后更新状态。出错时保留用户已经填的内容，把焦点放到出错位置。不要因为某一个字段错误就清空整个表单。

## 25.3 信号同步：怎样避免反复互相触发

问题：滑块改变数字框，数字框又改变滑块，会不会无限循环？

先观察每个控件在“值没有变化”时是否真的发信号。很多值属性仅在实际变化时发送，单纯同值回写不会无限递归。但业务槽还有日志、存盘等副作用时，重复触发仍可能有问题。

参考方案有三类：只让一个地方修改业务状态；更新界面时用 `QSignalBlocker` 暂时屏蔽信号；使用明确的同步标记。选择依据是副作用在哪里。屏蔽期间的信号不会在解除屏蔽后补发，如果别的订阅者也需要知道最终结果，要设计一次明确通知。

问题：循环中连接按钮，点击后都打印最后一个编号。

原因通常是闭包晚绑定。函数执行时才读取循环变量，而循环早结束了。常见适配方式为 `lambda checked=False, number=number: handle(number)`：默认参数保留当时值，同时给点击信号的布尔参数留位置。更复杂时写一个返回处理函数的普通工厂函数，避免把逻辑挤进一行。

## 25.4 对话框与生命期：显示、关闭和删除是不同动作

问题：点击按钮新建一个无父对象的非模态窗口，窗口一闪就没了。

提示：槽返回后，还有谁持有窗口的 Python 引用？参考思路是把窗口保存为 `self.dialog` 等属性，或结合父对象和明确的关闭策略管理它。仅仅在函数内写 `dialog = QDialog()` 再 `show()`，不能作为可靠的长期管理方式。

问题：已关闭的对话框重新 `show()` 报 C++ 对象被删除。

检查是否启用了 `WA_DeleteOnClose`，或者父对象已销毁。Python 引用还存在不代表底层 Qt 对象还活着。选择“关闭后复用”或“关闭后删除、下次重建”其中一种，并在整个逻辑中保持一致。

关闭确认参考逻辑：无修改直接接受；有修改询问；取消则忽略关闭；放弃则接受；保存时只有保存真正成功才接受。保存的返回值必须穿过对话框调用返回到关闭处理，不能把每一步都写成没有结果的 `None`。

## 25.5 数据显示：身份不能依赖屏幕位置

问题：排序后删除错行。

先问数据是 `QTableWidget` 里的条目，还是 `QTableView` 的源模型。前者应该把稳定编号存进 item data，后者在代理排序后应把视图索引 `mapToSource()` 再操作源模型。多行删除时，要先收集目标身份或源行，按合适顺序处理，避免删一行后后续行号整体移动。

问题：改了模型的 Python 列表，界面没更新。

模型视图不是每毫秒扫描你的列表。现有单元格改变需发送范围与 role 合适的 `dataChanged`；插入和删除需正确的 begin/end 通知；全量换数据才考虑 reset。不要为单个字符变化重置整个模型，这会影响选中、滚动和编辑状态。

问题：数字排序得到 1、10、2。

原因可能是给排序提供了字符串。显示文本和排序值可以不同：通过合适 role 返回数字，并让代理按该 role 排序。测试时用有区分度的数据，只有 1、2、3 很难暴露错误。

## 25.6 文件与线程：先分清成功的含义

问题：用户取消了保存选择，但程序显示“保存成功”。

参考路线：检查对话框返回的文件名 → 空字符串直接返回失败/取消 → 执行写入并捕获合理异常 → 成功后才改变 dirty、路径和提示。路径选择成功、文件打开成功、最终内容提交成功是不同阶段。

问题：有坏 JSON 时程序返回空列表，随后保存把旧文件覆盖了。

这把“确实是空数据”和“读取失败”混成一种结果。应让仓库抛出明确异常或返回能区分错误的结果，界面保持原状态并解释失败。读取失败不能自动变成一份可覆盖原文件的空文档。

问题：用了 `QThread`，界面仍卡住。

先在工作函数中观察当前线程。如果主线程直接调用 `worker.run()`，普通函数调用仍在调用线程执行；`moveToThread()` 不会改变 Python 普通调用规则。也可能是连接方式、耗时界面更新、主线程 `wait()`，或任务根本仍写在按钮槽里。

问题：取消信号连接了 worker.cancel，仍要等全部完成。

如果工作线程正在执行一个长槽，它的事件循环无法处理排队的取消槽。使用 `requestInterruption()` 并在工作循环中定期检查，或采用适合任务的可取消 I/O。中断请求本身不会打断无限阻塞的库函数，仍需设置超时或使用库提供的取消机制。

问题：运行中直接关闭导致 `QThread: Destroyed while thread is still running`。

先请求取消、暂时忽略关闭、保持线程及 worker 引用，等线程确实结束后清理并再次关闭。不要把 `terminate()` 当通用补丁；它可能在共享状态修改一半时切断执行。

## 25.7 进程、网络与架构

进程输出中文偶尔乱码，先检查编码是否一致，再检查一次 readyRead 是否只拿到了多字节字符的一部分。增量解码器保留不完整尾部，下一批字节到来时继续解码。每批输出不是完整行，追加显示也要考虑是否人为插入了多余换行。

网络的 `finished` 只说明本次请求结束。接下来仍需检查取消/网络错误、HTTP 状态、正文类型和解析失败。界面按钮应从实际请求状态恢复，不要只在成功路径启用。

架构练习的判断标准：把保存从 JSON 换成别的存储时，是否只需改仓库及装配？给数据规则写测试时，是否被迫打开窗口？页面之间是否通过访问对方十几个内部控件来通信？这些具体问题比背 MVC/MVP/MVVM 的缩写更有帮助。

## 25.8 参考项目的扩展提示

为第 22 章增加“仅看未完成”：把复选框状态读进 `_refresh()`，让一条任务同时满足名称条件与完成条件才显示。不要筛选时直接删 `self.tasks`。新增记录若不符合当前筛选，应在状态栏说明或保持统计一致，而不是假装没有添加成功。

增加编辑名称：先按编号找到目标，再弹输入对话框；取消则不动数据；确认后复用 Task 的规则创建替换对象；成功才标记修改。用编号定位，避免同名任务修改错对象。

迁移到表格模型：先保留 Task 和仓库，只替换数据展示与相关操作；再增加代理排序；最后验证搜索、选中和保存。一次把存储、模型、外观、线程全部重写，错误会很难隔离。

最后复盘时写三句话：我原本以为什么；实验实际证明什么；下一次遇到类似问题先检查什么。能持续回答这三句，你就在积累自己的开发经验。
