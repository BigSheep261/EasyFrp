# 第 18 章：项目结构与分层设计——让代码长大以后仍能修改

[上一章：网络请求与异步思维](17_网络请求与异步思维.md) · [阅读地图](00_阅读地图与学习方法.md) · [下一章：调试日志与测试](19_调试日志与测试.md)

本章目标：知道什么时候拆文件、按什么边界拆，以及如何让界面、业务规则和数据存储互相协作。你不需要一开始就拥有“大型项目架构”，需要的是每增加一个功能，仍能找到它应该放的位置。

## 1. 单文件不是错误，职责混在一起才会越来越难改

只有一个窗口、几十行代码时，单文件最方便阅读。问题通常出现在某个按钮槽同时做这些事情：读取控件、判断业务规则、拼 SQL、连接数据库、保存文件、更新列表、弹错误框。

当你想改保存格式时，必须担心窗口逻辑；想自动测试业务规则时，又必须启动 GUI。这说明功能之间的边界不清晰。

拆分的目标是让变化集中。例如把 JSON 改成 SQLite，主要修改存储代码；把窗口重新排版，不必修改“任务标题不能为空”这一条规则。文件数量增加本身不产生这样的效果，关键是职责和依赖方向。

## 2. 用任务管理器认识四个角色

假设我们做一个能新增任务、标记完成和保存数据的桌面程序：

| 角色 | 负责什么 | 不应负责什么 |
| --- | --- | --- |
| 界面 `views` | 控件、用户输入、反馈、显示状态 | 直接编写 SQL 或决定业务规则 |
| 业务 `services` | 新增、完成、删除的用例与验证 | 弹 `QMessageBox` 或读取输入框 |
| 数据对象 `domain` | 任务是什么、有哪些字段 | 建立窗口或数据库连接 |
| 存储 `repositories` | 读写 JSON、SQLite 等外部数据 | 决定按钮是否灰色 |

这不是唯一命名方式。不要因为看到 MVC、MVP、MVVM 就以为每个项目都必须照搬一整套术语。先能解释每个类为什么存在、由谁调用、能否独立替换，再选择模式。

Qt 的 Model/View 主要描述数据如何供列表、表格、树展示。这里的领域数据对象与 `QAbstractTableModel` 并不是同一个东西。你可以让表格模型把业务数据适配成 Qt 需要的行、列、角色，而不让它承担所有持久化逻辑。

## 3. 一个适合练习的目录

下面是示意结构，并非当前仓库已经具备的文件：

```text
任务管理器/
├─ main.py                    # 启动与依赖组装
├─ task_app/
│  ├─ __init__.py
│  ├─ domain.py               # Task 等普通 Python 对象
│  ├─ services.py             # 新增、完成、删除等用例
│  ├─ repositories.py         # 存储实现
│  ├─ views/
│  │  ├─ __init__.py
│  │  └─ main_window.py       # 主窗口
│  └─ resources/              # 只读图标等随程序发布的文件
└─ tests/
   ├─ test_services.py
   └─ test_window.py
```

`main.py` 只做组装：创建 `QApplication`，构造存储和业务对象，把业务对象传给窗口，显示窗口并进入事件循环。它像把零件装成整机的地方，不承担具体业务规则。

项目刚开始时 `domain.py` 和 `services.py` 完全可以先放一起。只有当阅读、修改或测试明显需要边界时再拆。不要给一个只有三个控件的练习预先建立二十个空目录。

## 4. 从一个完整用例看依赖方向

用户点击“新增任务”后，数据流可以是：

```text
输入框文本 → 窗口调用 service.add_task(text)
           → 业务对象校验标题并创建 Task
           → repository 保存
           → 返回 Task，窗口刷新并清空输入框
```

业务对象不会知道调用者是窗口、命令行还是测试。下面是可以独立理解的最小结构片段：

```python
from dataclasses import dataclass
from uuid import uuid4

@dataclass
class Task:
    id: str
    title: str
    completed: bool = False

class TaskService:
    def __init__(self, repository):
        self.repository = repository

    def add_task(self, title):
        clean_title = title.strip()
        if not clean_title:
            raise ValueError("任务标题不能为空")
        task = Task(id=str(uuid4()), title=clean_title)
        self.repository.add(task)
        return task
```

这是设计片段，不是可直接运行的 GUI。`repository` 必须提供 `add(task)`，且保存失败应抛出明确异常；调用者只有在函数正常返回后才认为新增成功。完整的可运行项目见[第 22 章综合实战](22_综合实战_桌面任务管理器.md)。

把依赖对象作为构造参数传入，通常称为依赖注入。它并不神秘：窗口不自己到处寻找数据库，调用者已经把它需要的能力递给它了。测试时可以传入简单内存仓库，正式运行时传入文件仓库。

## 5. 哪些通信使用信号，哪些直接调用

普通业务函数执行很快并有明确结果时，直接调用和返回值最易懂。不要把所有函数都换成信号，否则很难追踪谁做了什么。

事件需要通知多个观察者、耗时任务稍后才完成、控件产生用户动作时，信号很合适。例如 worker 发出完成信号，窗口更新界面；配置服务发出配置变更信号，多个页面刷新。

跨线程信号传复杂可变对象时要谨慎。`pyqtSignal(object)` 传递 Python 对象通常不会自动深拷贝；发送者随后修改同一个列表，接收者就可能看到变化中的状态。优先传不可变结果、数据副本，或约定传出以后不再修改。

Qt 信号通知与函数返回各有职责。试着为每次通信写一句话：“我需要立即得到结果”或者“我需要得知某件事已经发生”，选择就会清晰得多。

## 6. 状态要有唯一、清晰的来源

界面上显示“运行中”，不等于按钮文字本身就是业务状态。不要根据 `button.text() == "停止"` 决定是否停止任务；以后改成英文按钮就会破坏行为。

用明确的变量或枚举保存状态，例如 `Idle`、`Running`、`Stopping`；写一个函数依据状态统一设置按钮、提示文字和输入框可用性。状态变化发生在业务事件上，控件只负责展示。

同理，列表控件中的每一行不是数据的唯一保存位置。任务最好有稳定 ID，排序、筛选以后仍能识别同一个任务；不要拿行号当永远不变的任务编号。

## 7. 异常在哪一层处理

业务层发现输入不合法，可以抛 `ValueError` 或项目自己的异常；存储层发现磁盘不可写，可以传播 `OSError` 或转换成明确的存储异常。界面层决定如何向用户解释，并把技术详情交给日志。

不要每层都 `except Exception: pass`。错误被吞掉后，上层可能以为保存成功，用户直到重启才发现数据丢失。也不要每层都重复弹同一个错误框。

异步任务不能指望异常自动穿过线程边界返回调用者，所以前面的 worker 专门提供 `failed` 信号。无论采用哪种方式，失败都应该能被调用方观察到，并能恢复状态。

## 8. 项目增长的合理顺序

先跑通最小用例，再形成稳定的数据对象；把业务规则从按钮槽提取出来；把外部读写单独封装；最后补齐日志、测试和发布。每一步都有可运行版本，避免“拆完所有文件之前整个程序都不能用”。

发现循环导入时，先检查依赖是否反向：服务为什么需要导入窗口？仓库为什么需要主程序中的全局对象？通常把共用数据类型提取到低层模块，并让入口负责组装，就能解决根因。

函数设计也尽量写清契约：输入是什么、返回什么、哪些情况抛异常、是否改变对象状态、是否执行 I/O。类型标注可以帮助阅读，但不会自动校验所有运行时数据。

## 9. 练习与自检

1. 把一个按钮槽分成“读取输入、调用业务、展示结果”三段，业务函数不导入 PyQt6。
2. 为上面的 `TaskService` 写一个内存仓库，并用纯 Python 调用新增任务。
3. 把同一个业务对象传给两个简单界面，观察哪些代码可以直接复用。
4. 画出你的模块导入关系，检查是否出现服务依赖窗口的反向箭头。
5. 给每个类写一句职责说明；如果一句话里出现许多“同时还负责”，尝试进一步拆分。

自检：换保存格式主要改哪里？界面为什么不应拼 SQL？为什么任务要有稳定 ID？不用 Qt 是否也能测试标题验证？这些问题能直接检验你的分层是否真正有用。
