# 阶段 2：frpc 启停、状态与日志开发计划

创建日期：2026-11-06
当前状态：已进入阶段 2，以下功能待实施与验收。
所属总计划：[EasyFrp 开发计划](开发计划.md)

## 一、目标与范围

在现有 frpc 启动入口和 TOML 加载逻辑的基础上，完成“能可靠启停 → 能判断进程与连接状态 → 能查看运行与报错日志”的闭环。

严格按照以下顺序安排开发与验收：

1. 完善启停功能。
2. 完善进程状态与连接状态显示，并建立实际检测机制。
3. 完善运行与报错日志显示，并按级别区分文字颜色。

本阶段以 frpc 控制页及其进程服务为主要改动范围。frps 保持现有使用流程，涉及共用模块时进行回归检查；完整的 frps 监控、TOML 编辑和 Dashboard 仍由总计划后续阶段安排。

## 二、当前实现基线

以 2026-11-06 工作区源码为准：

- `src/frp_gui/ui/pages/frpc_control_view.py`：启动按钮仅连接 `start_frpc()`，尚未根据运行状态切换为停止操作或更新按钮反馈。
- `src/frp_gui/backend/frpc/process_service.py`：通过 `QProcess` 启动 frpc，并提供停止入口；已经定义进程、连接状态及对应信号，但状态更新处理尚未完成。
- 启动命令为 `frpc.exe -c <frpc.toml 路径>`，FRP 负责解析 TOML；发起启动请求不代表配置有效或连接成功。
- 当前停止方法包含同步等待，需要在交互停止流程中避免阻塞界面。
- 标准输出和标准错误均被重定向至空设备，当前无法在界面查看运行详情或错误原因。

原阶段 2 的启动命令、配置路径、工作目录、配置加载与退出清理梳理继续作为本阶段基础；已有认识可复用，未验证结论需要补齐记录。

## 三、2.1 完善启停功能

**目标：** 按钮始终反映真实进程生命周期，完成一次启动与完全停止的闭环。

| 时机或进程状态 | 按钮文字 | 是否可点击 | 行为与完成依据 |
| --- | --- | --- | --- |
| 初始未运行、完全停止后 | 启动 | 是 | 点击后发起启动；缺少程序或配置时给出明确错误 |
| 已接受启动请求，正在创建进程 | 启动中 | 否，按钮变灰 | 等待真实启动结果，禁止重复发起 |
| 进程已经运行 | 停止 | 是 | 点击后请求停止；此时不代表已经连接服务端 |
| 已接受停止请求，尚未完全退出 | 停止中 | 否，按钮变灰 | 等待退出确认，不能提前恢复启动 |
| 启动失败或进程异常退出 | 启动 | 是 | 确认进程未运行后恢复按钮，并显示失败原因 |

**任务：**

- [ ] 由后端统一维护进程状态，页面根据状态更新按钮文字、禁用样式和点击行为，避免页面自行假定操作成功。
- [ ] 启动前检查可执行文件、配置路径及当前进程状态，阻止重复启动；失败时提供可理解的提示。
- [ ] 使用 `QProcess` 的启动、状态变化、退出和错误事件确认结果；同时处理启动成功后立即退出的情况。
- [ ] 停止时先请求终止，使用非阻塞超时机制，超时后强制结束；强制结束后仍需等待进程退出确认。
- [ ] 防止重复停止、遗留超时回调及旧事件影响下一轮启动，保持单个受管理进程实例。
- [ ] 处理窗口关闭与进程清理，保证退出后不遗留本应用启动的 frpc。

**验收标准：** 完整观察到“启动 → 启动中（灰）→ 停止 → 停止中（灰）→ 启动”；快速连点不会重复创建进程；启动失败、异常退出和停止超时后按钮都与实际进程一致，等待期间窗口仍可响应。

## 四、2.2 完善状态连接显示与检测

**目标：** 分别显示“进程是否运行”和“frpc 是否连接服务端”，并持续检测变化。

| 状态维度 | 显示范围 | 判断依据 |
| --- | --- | --- |
| 进程状态 | 程序未找到、未运行、启动中、运行中、停止中；异常时附原因 | 可执行文件检查、`QProcess` 实际状态、启动错误及退出事件 |
| 连接状态 | 未连接、连接中、在线、重连中；无法判断时显示未知 | 目标 FRP 版本可验证的连接事件或接口，不能仅依据进程存活 |

**任务：**

- [ ] 分开维护、发送并展示进程状态与连接状态，页面首次打开时读取当前状态，后续通过信号同步。
- [ ] 进程运行但尚未确认登录成功时显示“连接中”；获得可靠成功证据后才显示“在线”。
- [ ] 核对当前使用的 FRP 版本、实际日志和可用接口，明确登录成功、断开及重试的识别依据，并记录样例。
- [ ] 优先复用可靠连接事件或受认证的本地接口；如采用日志检测，仅引入本项所需的后台输出消费与解析，界面日志展示仍在 2.3 完成。
- [ ] 确定断线检测与恢复机制。无法获得可靠断开事件时，使用有超时的受支持状态查询；证据不足、日志规则不匹配或查询失败时显示“未知”及原因，不能长期沿用旧的在线状态。
- [ ] frpc 保持运行但断线、重新连接时及时更新状态；进程退出或完全停止时清除旧的连接状态，显示“未连接”。
- [ ] 明确进程错误、配置错误和网络连接错误的归属；服务端登录成功不等于所有代理可用，代理状态留给后续 Dashboard。

**验收标准：** 进程运行但服务端不可达时不会显示在线；服务端恢复后按真实证据更新连接结果；连接中断、自动重连、检测不可用及进程退出均有准确反馈。检测过程不阻塞界面，不会因上一轮进程的历史记录误报当前在线。

## 五、2.3 完善日志显示

**目标：** 在控制页持续展示运行日志和报错日志，用户能通过文字级别与颜色快速区分。

| 日志类型 | 建议文字颜色 | 文字标记与规则 |
| --- | --- | --- |
| 普通运行信息 | 当前主题下清晰可读的默认前景色 | `INFO`，保留启动、连接、停止等运行信息 |
| 警告 | 橙色或黄色，需保证对比度 | `WARN`，用于重试或可恢复异常等警告信息 |
| 错误 | 红色，需保证对比度 | `ERROR`，展示 FRP 报错及应用检测到的启动、进程错误 |

**任务：**

- [ ] 取消将标准输出和标准错误丢弃的配置，使用异步读取持续消费两个通道；复用 2.2 已建立的读取入口，避免重复消费或重复连接信号。
- [ ] 将后端日志事件与页面展示分离，日志事件包含时间、级别、来源和内容，连接检测与界面共享同一份解析后的输入。
- [ ] 优先按 FRP 明确输出的级别分类；无级别的标准错误作为错误、标准输出作为普通信息兜底，避免仅凭通道覆盖已有级别。
- [ ] 处理多字节字符、跨次读取的半行、换行和退出时的剩余输出，防止乱码、截断或重复显示；去除终端颜色控制码，按界面规则着色。
- [ ] 将缺少程序、配置错误、启动失败、异常退出和停止超时等应用侧事件同步写入日志，保留可诊断原因。
- [ ] 设置日志区最大保留行数，并同步限制后台缓存，持续运行时淘汰较早记录，避免内存无限增长；初始建议保留最近 2000 行，实施时记录最终值。
- [ ] 处理自动滚动：用户停留底部时跟随新日志，向上查看历史时保留阅读位置；日志作为纯文本展示，避免内容被误当作富文本。
- [ ] 在实际浅色或深色主题下验证文字对比度，并保留级别文字，使用户无需只靠颜色判断。

**验收标准：** 正常运行能实时看到日志；错误信息以不同颜色和明确级别展示；中文、分段输出和最后一段无换行内容可正确显示；高频日志不明显卡住界面，记录数达到上限后按规则淘汰。

## 六、顺序与依赖处理

2.1 先完成进程控制所必需的生命周期状态，2.2 再补全状态展示与业务连接检测。若连接检测依赖日志，2.2 可以先建立最小后台日志采集与解析能力；2.3 负责完整分类、着色和显示体验，开发验收顺序仍保持不变。

完成本阶段后再进入总计划阶段 3。阶段 8 Dashboard 复用已经验证的状态与日志基础，并单独验证流量、代理等监控数据来源。
