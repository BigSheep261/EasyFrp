# EasyFrp 开发计划

创建日期：2026-10-31  
当前状态：规划中，尚未开始本计划中的功能开发。

## 一、目标与推进原则

按照“理解现有实现 → 恢复配置编辑 → 模块化与持久化 → 设置与运行模式 → 运行监控 → 样式完善”的顺序推进，让每一步都建立在已经理解并验证的功能上。

本计划对应以下九项工作：

1. 整理 frpc、frps 的 View 与核心逻辑，掌握信号与槽的绑定方式。
2. 掌握核心启动 FRP、加载对应 TOML 配置的过程。
3. 恢复 frpc、frps 的 TOML 编辑页面。
4. 完善 TOML 页面的具体功能，按模块组织配置并引入 SQLite。
5. 添加设置页面。
6. 添加开机自动启动设置。
7. 添加 C/S 模式切换设置。
8. 添加 Dashboard，展示连接状态、流量等信息。
9. 统一并美化界面样式。

实施时，每个阶段分别记录学习结论、代码改动和验证结果。先完成最小闭环，再增加复杂功能；规划中的推荐方案不代表已经实现或已经确定的产品行为。

## 二、当前代码基线

以下结论基于编写本文时的工作区；后续重构应同步更新相关说明。

| 位置 | 当前职责 |
| --- | --- |
| `main.py`、`src/frp_gui/app.py` | 应用入口、运行目录初始化、Qt 应用和主窗口创建 |
| `src/frp_gui/ui/main_window.py` | 创建 frpc、frps 控制页，注册导航，退出时清理进程 |
| `src/frp_gui/ui/weights/main_tab.py` | 侧边标签和横向文字绘制 |
| `src/frp_gui/ui/pages/frpc_control_view.py` | frpc 控件、用户交互、状态与错误展示 |
| `src/frp_gui/ui/pages/frps_control_view.py` | frps 控件、用户交互、状态与错误展示 |
| `src/frp_gui/backend/frpc/process_service.py` | frpc 进程启停、状态维护和错误通知 |
| `src/frp_gui/backend/frps/process_service.py` | frps 进程启停、状态维护和错误通知 |
| `src/frp_gui/utils/paths.py` | 源码与打包环境的路径定位、目录和空配置初始化 |
| `config/frpc.toml`、`config/frps.toml` | 当前交给 FRP 的配置文件 |

当前项目没有独立命名为 `core` 的目录。本文中的“核心”指现有后端进程服务，以及未来拆分出来的配置、存储、设置和监控服务，不要求为了统一名称而先移动代码。

当前只有手动进程控制，没有 TOML 编辑、应用设置、SQLite 或 Dashboard。服务通过 `QProcess` 启动 FRP，并将标准输出和标准错误丢弃；“运行中”只表示子进程已启动，不能证明客户端已连接服务端或代理已可用。

## 四、分阶段任务

### 阶段 1：整理 frpc、frps 的 View 与核心逻辑

**目标：** 能从一个页面操作准确追踪到后端方法，并说明状态如何返回界面。

- [ ] 阅读应用入口、主窗口、两端控制页和进程服务，列清每个类的职责、创建位置和生命周期。
- [ ] 整理信号槽清单，记录信号发送者、信号参数、连接位置、接收方法及产生的界面变化。
- [ ] 追踪 `open_switch.toggled → _handle_switch_toggled → start_frpc()/stop_frpc()`，再对照 frps 的对应路径。
- [ ] 追踪 `QProcess.started/finished/errorOccurred → 服务内部处理方法 → state_changed/error_occurred → 页面更新`。
- [ ] 说明 `_syncing_switch` 如何避免 `setChecked()` 引起重复启停，以及启动中、停止中禁用按钮的原因。
- [ ] 记录两端的共性与差异，再决定是否值得提取共用逻辑，避免在理解之前大规模重构。

**交付物：** 一份源码学习记录，包含职责表、信号槽对照表，以及启动、停止、异常退出三条调用链。

**验收标准：** 不依赖逐行阅读整个项目，就能解释“谁接收点击、谁启动进程、谁维护状态、谁更新控件”；能说明页面切换为何不会停止进程，以及窗口关闭如何触发清理。

### 阶段 2：搞懂核心如何启动 FRP 并加载 TOML

**目标：** 掌握实际启动命令、配置来源、工作目录和异步状态的含义。

- [ ] 梳理 `ensure_runtime_directories()`、默认路径和服务构造参数之间的关系，区分源码运行与打包运行。
- [ ] 对照实际代码记录启动过程：检查程序和配置是否存在、设置 `starting`、设置工作目录、调用 `QProcess.start()`。
- [ ] 明确启动形式为 `frpc.exe -c <frpc.toml 路径>` 或 `frps.exe -c <frps.toml 路径>`，配置内容由 FRP 解析，当前 GUI 只检查文件存在。
- [ ] 说明子进程工作目录是对应可执行文件所在目录，检查 TOML 中相对路径的实际解析位置。
- [ ] 区分“提交启动请求”“系统创建子进程”“FRP 配置有效”“连接或代理就绪”，避免把方法返回值与业务成功混为一谈。
- [ ] 梳理正常停止、超时强制结束、异常退出、应用退出清理的状态变化。
- [ ] 在准备好的测试环境验证缺少程序、缺少配置、非法 TOML、端口占用等情况，记录可见提示和可诊断信息的缺口。

**交付物：** 启停流程说明、配置路径说明、常见失败场景与排查记录。

**验收标准：** 能解释修改哪个文件会影响哪一个进程、何时需要重启，以及为什么空 TOML 的存在不代表配置可用；能定位启动失败发生在哪一层。

### 阶段 3：恢复 frpc、frps 的 TOML 编辑页面

**目标：** 先恢复从文件读取、编辑、保存并用于启动的完整闭环。

- [ ] 如仓库历史中存在旧页面，先核对其行为和适配成本，再决定恢复或重建；不直接把旧实现视为当前需求。
- [ ] 为 frpc、frps 分别添加配置编辑入口，明确当前编辑的配置文件路径。
- [ ] 实现原始 TOML 文本的加载、编辑、语法校验、保存和重新加载。
- [ ] 为未保存修改提供明确标记，在切换配置、重新加载或关闭时处理保存、放弃和取消。
- [ ] 保存采用临时文件替换等方式，降低写入中断损坏原配置的风险；权限或磁盘错误应保留编辑内容并提示原因。
- [ ] 将“保存成功”与“运行配置已生效”分开提示，初期通过停止后重新启动来应用修改，不默认承诺热加载。
- [ ] 确保编辑目标与进程服务的 `config_path` 一致，避免保存了一份文件、启动时却使用另一份。

**交付物：** 两端 TOML 编辑页面，以及文件读写、语法校验的独立服务。

**验收标准：** 两端均可完成“读取 → 修改 → 校验 → 保存 → 重启使用”；无效 TOML 不覆盖正常配置；取消操作不丢失未保存内容；进程启停功能保持可用。

### 阶段 4：完善 TOML 功能，模块化加载并引入 SQLite

**目标：** 从基础文本编辑升级为可维护的模块化配置管理。

- [ ] 根据实际使用的 FRP 版本列出支持字段与模块边界，区分 TOML 语法校验和 FRP 字段、取值、组合规则校验。
- [ ] frpc 优先支持服务端地址、端口、认证和代理列表；代理条目支持新增、修改、删除及必要校验，再逐步扩展其他字段。
- [ ] frps 优先支持监听和认证配置，并为后续 Dashboard 所需的管理接口配置预留模块；具体字段按目标 FRP 版本核对。
- [ ] 将模块拆成独立编辑组件，通过模块注册或工厂按角色加载；控件展示、配置规则、存储和 TOML 转换分别负责。
- [ ] 保留原始 TOML 编辑或高级配置入口。结构化表单与原文转换时保留未支持字段，并评估注释、字段顺序和格式的保留方式。
- [ ] 引入 SQLite，规划配置方案、配置内容、当前选中方案、应用设置和数据库版本等必要数据；提供事务和版本迁移机制。
- [ ] 支持配置方案的新增、修改、复制、删除、选择，以及 TOML 导入、导出；删除当前方案时要求先完成安全切换。
- [ ] 设计首次导入已有 TOML 的流程，避免初始化数据库时覆盖现有配置；认证信息不得写入调试输出，数据库文件也应按敏感配置管理。

**推荐的数据流，实施前确定：** SQLite 保存配置方案及其权威配置内容；启动前从已保存的方案生成并校验运行 TOML，FRP 继续通过 `-c` 读取文件。运行 TOML 是导出产物，外部修改通过显式导入进入数据库，避免数据库和文件同时被当作权威来源。

数据库事务与文件替换不是同一个原子操作：导出失败必须提示且阻止使用旧文件冒充新配置启动。阶段 3 的直接文件编辑在本阶段需要明确迁移为方案编辑，不能保留两套互相覆盖的保存流程。

**交付物：** 配置模块、配置方案服务、SQLite 存储层、TOML 导入导出与迁移说明。

**验收标准：** 模块可分别维护；多套方案重启应用后仍能恢复；导入导出不丢失未支持字段；数据库保存失败、导出失败和校验失败都有明确反馈；最终启动文件对应用户选中的已保存方案。

### 阶段 5：添加设置页面

**目标：** 建立统一的应用设置入口和持久化流程。

- [ ] 在主窗口注册设置页面，建立设置加载、修改、保存及失败反馈流程。
- [ ] 将设置与 FRP 业务配置区分：应用行为由设置服务管理，FRP 连接与代理参数仍由配置方案管理。
- [ ] 优先提供后续所需的自启动、C/S 模式设置区域；监控刷新周期等设置随对应功能开放，避免出现无效开关。
- [ ] 复用 SQLite 存储基础，通过独立设置服务提供默认值、校验和读写接口，页面不直接执行 SQL。
- [ ] 为设置标明立即生效、下次启动生效或需要重启 FRP，处理保存失败后的界面状态。

**交付物：** 设置页面、设置服务、持久化结构和生效规则说明。

**验收标准：** 首次启动有合理默认值；保存后重启应用仍能恢复；失败时不显示虚假的成功状态；设置修改不意外覆盖 FRP 配置。

### 阶段 6：添加开机自动启动功能

**目标：** 在设置页可靠开启和关闭 Windows 自启动。

- [ ] 先确定“开机自启动”指用户登录后启动 EasyFrp，还是无人登录时也运行。推荐第一版采用当前用户登录后启动，无人登录运行属于 Windows 服务等另一套实现。
- [ ] 区分“自动启动 EasyFrp”与“EasyFrp 启动后自动运行 frpc/frps”；后者是否需要、启动哪一端及哪套方案，实施前单独确定。
- [ ] 比较当前用户的启动项注册方式，选择一种实现并封装为平台服务，避免在页面内直接操作系统注册信息。
- [ ] 注册时正确处理程序路径、参数和包含空格的目录；明确开发态与打包态的支持范围。
- [ ] 查询系统实际注册状态，设置开关以真实结果为准；处理权限失败、路径失效和重复注册，关闭开关后清除本应用创建的启动项。

**交付物：** 自启动服务、设置页交互及 Windows 验证记录。

**验收标准：** 开启后按约定在登录或启动场景运行；关闭后不再自启动；重复操作不会产生重复项；失败时显示原因并保持开关与系统状态一致。

### 阶段 7：添加 C/S 模式切换功能

**目标：** 让用户选择需要使用的角色，并保持页面、配置和进程行为一致。

- [ ] 确定 C/S 模式含义：本文暂按 C 为 frpc 客户端、S 为 frps 服务端规划；是否保留两端同时使用的模式，需要实施前确认。
- [ ] 明确模式影响范围：导航入口、默认页面、可选配置方案，以及 Dashboard 的展示对象。
- [ ] 明确运行中切换策略。推荐在受影响进程停止后再切换；若提供停止并切换操作，应先处理未保存修改并等待停止完成。
- [ ] 将模式保存到设置，下一次启动恢复；未选择的角色配置保留，不因隐藏页面而删除。
- [ ] 保持进程服务的归属清晰，导航重建或页面隐藏不应留下无法控制的后台进程，也不应重复创建服务和连接信号。

**交付物：** 模式设置、页面联动、进程处理策略及持久化。

**验收标准：** 切换后可见页面、活动方案和 Dashboard 对象一致；运行中切换按明确规则执行；两端配置互不覆盖；重启应用后恢复已保存模式。

### 阶段 8：添加 Dashboard

**目标：** 展示真实、可解释的连接状态和流量信息。

- [ ] 先验证目标 FRP 版本提供的管理 API 或指标接口，分别建立 frpc、frps 的可用数据清单，核对认证方式、响应字段、单位和刷新限制。
- [ ] 分开定义进程状态、客户端连接状态和代理状态；frps 本地监听状态与已连接客户端数量也分别展示，不把进程存活直接标为连接正常。
- [ ] 第一版优先展示当前角色、配置方案、进程状态、可获取的连接或代理信息、累计入站与出站流量；实时速率仅在数据来源可靠时提供。
- [ ] 标明流量方向和统计范围，例如以服务端、客户端还是某条代理为视角，以及累计值从哪个时刻开始计算。
- [ ] 如接口返回累计字节数，通过相邻采样差值和时间间隔计算速率，处理首次采样、进程重启、计数归零和采样失败。
- [ ] 将采集服务、数据模型和展示页面分离，使用异步请求或后台任务，设置超时，避免阻塞界面或叠加未完成请求。
- [ ] 数据不可用时显示“未启用”“不支持”“认证失败”或“暂时无法获取”等准确状态，保留最后更新时间，不以零值冒充成功读取。
- [ ] 管理接口优先使用受认证的本地访问方式；frpc 与 frps 能力不一致时分别展示实际支持的信息，不为补齐界面而扩大管理接口暴露范围。

当前程序丢弃进程输出，因此不能直接假设已有日志可解析。如果最终需要日志作为补充来源，应另行设计持续消费、容量限制和解析规则；历史曲线持久化作为后续扩展，不默认加入第一版。

**交付物：** 指标来源与能力表、采集服务、Dashboard 页面和异常状态说明。

**验收标准：** 界面明确区分进程与业务连接状态；支持的指标能与数据源核对；不支持的指标有说明；断网、认证失败、FRP 停止或重启时不会卡住界面、保留虚假的在线状态或产生负速率。

### 阶段 9：美化样式

**目标：** 在功能稳定后统一页面视觉和交互反馈。

- [ ] 统一导航、标题、按钮、表单、配置模块、状态标签和 Dashboard 的字号、间距、颜色与圆角。
- [ ] 将通用 QSS 和必要资源集中管理，减少散落在页面中的重复样式。
- [ ] 统一正常、悬停、选中、禁用、加载中和错误状态，连接状态同时使用文字或图标表达。
- [ ] 检查配置长文本、错误提示、代理列表与 Dashboard 的空间分配，结合当前固定窗口尺寸决定是否支持调整窗口大小。
- [ ] 验证 Windows 常用显示缩放、键盘焦点、Tab 顺序和文本可读性，确保美化后操作仍然清晰可达。

**交付物：** 统一样式资源、主要页面截图和显示适配记录。

**验收标准：** 各页面视觉一致；常用缩放下无关键控件遮挡；状态清晰可读；样式改动不影响信号连接、按钮可用性或业务流程。

## 五、实施前需要确定的事项

这些问题不会阻塞本文档建立，在开发到对应阶段前逐项确定即可。

| 问题 | 影响阶段 | 推荐起点 |

## 六、里程碑与验证方式

| 里程碑 | 完成条件 | 验证重点 |
| --- | --- | --- |
| M1：理解现有架构 | 阶段 1、2 完成 | 能独立说明信号槽、启停、配置加载和退出清理 |
| M2：恢复配置编辑 | 阶段 3 完成 | 两端编辑、校验、保存、重新启动的闭环 |
| M3：配置管理与设置基础 | 阶段 4、5 完成 | 方案持久化、数据迁移、导入导出与设置恢复 |
| M4：运行行为可配置 | 阶段 6、7 完成 | 系统自启动状态、角色切换和进程一致性 |
| M5：运行状态可观察 | 阶段 8 完成 | 真连接状态、流量口径、异常与恢复 |
| M6：可交付界面 | 阶段 9 完成 | 主要流程回归、显示适配与打包环境验证 |

每次涉及功能修改，按影响范围进行验证：配置转换与校验、SQLite 事务与迁移、流量计算等适合自动化验证；进程启停、Windows 自启动和实际 FRP 接口需要在准备好的环境中集成验证；页面切换、未保存提示和显示适配需要界面验收。

不预设固定工期。完成阶段 1、2 后，根据配置模块数量、旧页面可复用程度和监控接口能力评估后续工作量。每个里程碑完成后更新复选框、验证结论及后续待办。
